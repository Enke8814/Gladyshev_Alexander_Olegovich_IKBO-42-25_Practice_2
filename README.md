## 1. Общее описание

CLI-инструмент для анализа зависимостей пакетов npm. Выполнены этапы 1–4:
загрузка настроек из XML, получение прямых зависимостей из HTTP-реестра npm
и построение транзитивного графа обходом BFS без рекурсии, вывод порядка
загрузки метаданных зависимостей.
Для получения данных используются `urllib` и `json` стандартной библиотеки:
сам менеджер npm и сторонние библиотеки не вызываются. Дополнительные
Визуализация появится на следующем этапе.

## 2. Функции и настройки

Запуск принимает `--config ПУТЬ` к XML-файлу (по умолчанию
`config.example.xml`). Настройки указываются только в XML:

| Элемент | Значение |
|---|---|
| `package` | имя npm-пакета (`express`, `@scope/name`); в тестовом режиме только большие латинские буквы (`A`) |
| `repository` | URL HTTP(S) реестра npm или путь к тестовому файлу |
| `test_mode` | `true` для файла, `false` для URL реестра |
| `output` | имя будущего SVG-файла, например `graph.svg` |
| `max_depth` | максимальная глубина обхода, целое число от 0 |

Относительные пути к файлу репозитория и к SVG отсчитываются от каталога
XML-файла. Для `output` каталог уже должен существовать. SVG-файл ещё не
создаётся. Ошибки конфигурации выводятся в stderr с кодом завершения 2;
ошибки HTTP и формата данных npm — с кодом 1.

Для обычного режима программа запрашивает метаданные по адресу
`<repository>/<package>` с заголовком
`Accept: application/vnd.npm.install-v1+json`. Для пакета с областью
видимости `/` кодируется как `%2F`. Из `dist-tags.latest` определяется версия,
затем из `versions[latest].dependencies` берутся **прямые обычные зависимости**
и диапазоны их версий. `devDependencies`, `peerDependencies` и
`optionalDependencies` в граф не входят. Для каждого посещённого пакета
запрашивается его версия `latest`. Диапазоны версий родительских зависимостей
пока не разрешаются: поэтому граф может отличаться от дерева установки npm.

Обход BFS хранит очередь и минимальную глубину каждого пакета. Корень имеет
глубину 0. Для пакетов на `max_depth` дальнейшие запросы не выполняются;
повторно встреченные пакеты не посещаются, но ведущие к ним рёбра сохраняются.
Это позволяет показать общие и циклические зависимости без зацикливания.
Обход сохраняет порядок извлечения из очереди: корень, затем пакеты первого
уровня, затем второго и так далее. Имена соседей сортируются, поэтому
порядок воспроизводим. Вывод этапа 4 показывает этот порядок с нумерацией.
Это порядок **запросов метаданных**, а не хронология физической установки:
npm может скачивать пакеты параллельно, разрешает диапазоны версий и
переиспользует уже установленные зависимости.

В тестовом режиме `repository` указывает на JSON-файл: объект, где ключи —
имена пакетов большими латинскими буквами, а значения — списки имён прямых
зависимостей. Пустой список задаёт пакет без зависимостей. Имя корневого
пакета должно быть ключом в файле; неописанные пакеты, встречающиеся в
списках зависимостей, считаются листовыми узлами.

```json
{"A": ["B", "C"], "B": ["D"], "C": ["D"], "D": []}
```

Структура проекта: `src/main.py` — CLI, `src/dependency_graph/config.py` —
чтение и проверка XML, `src/dependency_graph/registry.py` — клиент npm,
`src/dependency_graph/graph.py` — BFS и тестовые данные, `examples/` —
проверочные графы и конфигурации, `tests/` — автоматические проверки,
`run.sh` — запуск.
Применяется только стандартная библиотека Python.

## 3. Запуск и тесты

Нужен Python 3.10+. В корне репозитория:

```bash
./run.sh
./run.sh --config config.example.xml
./run.sh --config examples/branching.xml
./run.sh --config examples/cycle.xml
./run.sh --config examples/isolated.xml
./run.sh --help
./run.sh test
```

## 4. Примеры использования

Пример тестового запуска (`examples/branching.xml`):

```text
$ ./run.sh --config examples/branching.xml
Порядок загрузки зависимостей A (максимальная глубина 2):
1. A (глубина 0)
2. B (глубина 1)
3. C (глубина 1)
4. D (глубина 2)
5. E (глубина 2)
```

`examples/cycle.xml` выдаёт `A, B, C` без повторной загрузки A;
`examples/isolated.xml` — только корень. Ограничение глубины 0 также
выводит только корень. По умолчанию
`config.example.xml` использует реальный npm-реестр и глубину 1, чтобы
запрашивать только метаданные корневого пакета.

Для проверки ошибок скопируйте `config.example.xml` и поменяйте по одному
полю: `package` на `Bad Name`, `repository` на `not-a-url`, `test_mode` на
`maybe`, `output` на `graph.png`, `max_depth` на `-1`. Программа выдаст
сообщение с названием ошибочного поля. Тесты также проверяют тестовый режим,
ошибки XML и отсутствующие файлы. Проверки HTTP подменяют ответ маленькими
JSON-фикстурами, чтобы не зависеть от сети и текущих версий npm. Тесты BFS
проверяют минимальную глубину, циклы и границу обхода.

### Сравнение с npm

Пример с реальным реестром: создайте XML по образцу `config.example.xml`,
замените пакет на `is-odd` и глубину на `2`. На момент проверки программа
выдала порядок `is-odd → is-number`. Для независимого сравнения выполнены:

```bash
npm install --prefix /tmp/practice2-npm-compare --ignore-scripts \
  --no-audit --no-fund is-odd@3.0.1
npm ls --prefix /tmp/practice2-npm-compare is-odd is-number --all
```

`npm ls` показал `is-odd@3.0.1 → is-number@6.0.0`. Набор имён в этом
примере совпадает с обходом, но наш клиент берёт для каждого узла версию
`latest` (`is-number@7.0.0`), а npm устанавливает совместимую с диапазоном
родителя `^6.0.0`. Кроме того, `npm ls` показывает дерево установленного,
а не порядок загрузки; по его выводу нельзя установить фактическую
хронологию скачивания. В этом сравнении не утверждается совпадение версий
или порядка сетевых запросов npm.
